# メモ・添付ファイルのオフライン仕様とクラウド同期ガイド

最終更新日: 2026-01-18

RinSecretary のメモ機能は、インターネット接続がない状態でも快適に利用できる「オフラインファースト設計」を採用しています。
このガイドでは、オフライン時の動作、クラウドとの同期タイミング、ファイルのキャッシュ戦略について詳しく解説します。

---

## 1. オフライン機能の概要

### 1.1 どんな時でも使える「ローカルファースト」設計

RinSecretary は、すべてのデータをまず**あなたのデバイス内**（ブラウザの IndexedDB）に保存します。
そのため、以下のような状況でも問題なく動作します。

- 飛行機の中や地下鉄など、電波が届かない場所
- Wi-Fi が不安定な環境
- モバイルデータ通信を節約したい時

> [!NOTE]
> **技術的な仕組み**
> - クライアント側: `IndexedDB` (Dexie.js) でデータを管理
> - サーバー側: `PostgreSQL` (Prisma) でクラウドバックアップを保持
> - ファイルキャッシュ: `Service Worker` + `IndexedDB` のハイブリッド方式。メモ（本文）は同期時に一括取得されますが、添付ファイルは必要に応じて取得されます。

### 1.2 オフライン時にできること・できないこと

| 操作 | オフライン時の動作 |
|:---|:---|
| ✅ メモの新規作成 | **可能** - デバイスに即座に保存され、一覧に表示されます |
| ✅ メモの編集 | **可能** - 変更内容はローカルに保存され、オンライン復帰時に自動同期 |
| ✅ メモの削除 | **可能** - ローカルで削除され、同期時にサーバーからも削除 |
| ✅ ファイル添付（新規） | **可能** - ファイルはデバイスに保存され、プレビュー表示も可能 |
| ✅ 添付ファイルの閲覧 | **条件付き** - キャッシュ済みなら表示可能、未キャッシュは不可 |
| ❌ 他デバイスの最新データ取得 | **不可** - オンライン復帰まで古いデータのまま |
| ❌ 未キャッシュファイルの初回表示 | **不可** - ネットワーク接続が必要 |

## 2. クラウド同期の仕組み

### 2.1 同期が自動で始まるタイミング

以下の4つのタイミングで、自動的にクラウドとの同期処理が開始されます。

1. **アプリを開いた時**（ページ読み込み時）
2. **オフラインからオンラインに復帰した時**
3. **メモを保存した直後**（即座に同期を試行）
4. **手動で「同期」ボタンを押した時**

> [!IMPORTANT]
> **同期中に編集した場合**
> 同期処理中に新たな編集を行った場合、その変更は次回の同期でサーバーに送信されます。
> 同期処理は自動的にキューイングされるため、データが失われることはありません。

### 2.2 同期の流れ（詳細）

同期は以下の順序で実行される。

#### ステップ1: メモデータの同期

1. **Push（アップロード）**
   - ローカルで作成・編集されたメモ（`isDirty: true` のマーク付き）をサーバーへ送信
   - 削除されたメモ（`isDeleted: true`）の削除リクエストを送信

2. **競合チェック（Conflict Detection）**
   - サーバー側で更新時刻を比較
   - 同じメモが別のデバイスで同時に編集されていた場合、競合として検出
   - 競合が見つかった場合は、ユーザーに選択肢を提示（後述）

3. **Pull（ダウンロード）**
   - 最終同期時刻以降にサーバー上で更新されたメモを受信
   - ローカル DB に反映（`isDirty: false` として保存）

4. **削除の反映**
   - サーバー上で削除されたメモをローカルからも完全に削除

#### ステップ2: 添付ファイルの同期

メモの同期が正常に完了した後、添付ファイルの同期が開始されます。

1. **アップロード**
   - 未送信の添付ファイル（`isDirty: true` かつ `blob` を持つもの）を順次アップロード
   - 成功時: サーバーパス（`filePath`）を保存し、`isDirty: false` に更新
   - **重要**: アップロード後もファイル実体（Blob）はキャッシュとして保持されます

2. **削除**
   - 削除マーク付きファイル（`isDeleted: true`）をサーバーから削除
   - 成功時: ローカル DB からも完全に削除

3. **メタデータの取得**
   - サーバーから新規・更新された添付ファイルの**メタデータのみ**を受信。
   - ファイル実体（Blob）は自動ダウンロード**しません**（帯域節約のため）。
   - 実際のファイルは、ユーザーが閲覧した瞬間に Service Worker が取得（遅延読み込み）し、条件を満たせばキャッシュされます。

### 2.4 【重要】メモと添付ファイルのキャッシュタイミングの違い

RinSecretary では、通信量とオフラインの利便性のバランスを取るため、データ種別によって取得タイミングを分けています。

| データ種別 | 取得タイミング | 理由 |
|:---|:---|:---|
| **メモ（全文）** | **詳細/編集画面を開いた時のみ** | 100億件規模を想定し、全文は必要になるまで取得・キャッシュしない。 |
| **キャッシュ済みメモ** | **同期時に更新** | 一度キャッシュしたメモは、同期時にサーバーの最新データで更新される。 |
| **添付ファイル（実体）** | **閲覧時にオンデマンド** | 画像や動画はサイズが大きいため。 |

> [!TIP]
> **オフラインで全文を読むには？**
> 一度オンライン状態でメモの詳細画面または編集画面を開くと、全文がキャッシュされます。
> その後はオフラインでも閲覧・編集可能で、同期時に最新の内容に更新されます。

### 2.5 オフライン時の動作

| 画面 | オンライン時 | オフライン時（キャッシュ済み） | オフライン時（未キャッシュ） |
|:---|:---|:---|:---|
| メモ一覧 | サーバーから取得 + ローカルをマージ | ローカルのみ表示 | ローカルのみ表示 |
| メモ詳細 | サーバーから取得 → キャッシュ | IndexedDB から取得 | エラー表示 |
| メモ編集 | サーバーから取得 → キャッシュ | IndexedDB から取得 | エラー表示 |

---

### 2.5 競合（コンフリクト）が発生した時

複数のデバイスで同じメモを同時に編集した場合、以下の3つの選択肢が表示されます。

| 選択肢 | 動作 | いつ使う？ |
|:---|:---|:---|
| **サーバー優先** | サーバーのデータを正として、ローカルの変更を破棄 | 他のデバイスでの編集が正しい場合 |
| **ローカル優先** | ローカルのデータを正として、サーバーへ強制上書き | このデバイスでの編集が正しい場合 |
| **キャンセル** | 同期を中断し、次回同期時に再度通知 | どちらを選ぶか判断できない場合 |

> [!WARNING]
> **「ローカル優先」を選ぶと、他のデバイスでの変更は完全に失われます。**
> 慎重に選択してください。

## 3. 添付ファイルのキャッシュ戦略

### 3.1 自動キャッシュの仕組み

RinSecretary は、一度表示したファイルを自動的にデバイスに保存（キャッシュ）します。
これにより、2回目以降はオフラインでも瞬時に表示できます。

#### キャッシュされる条件

以下の**すべての条件**を満たすファイルが自動キャッシュされます。

1. ネットワークからの取得に成功した
2. ファイルサイズが **5MB 以下**（`OFFLINE_FILE_SIZE_LIMIT`）
3. デバイスのストレージに十分な空き容量がある

> [!TIP]
> **5MB を超えるファイルはどうなる？**
> 5MB を超えるファイルは自動キャッシュされませんが、オンライン時には問題なく表示できます。
> オフライン時に表示したい場合は、事前にオンライン状態で一度開いておく必要があります。

### 3.2 キャッシュの種類と優先順位

Service Worker は、以下の2種類のリクエストを異なる方法でキャッシュします。

#### 3.2.1 通常ファイル（`/api/uploads/*`）

**Cache First 戦略** を採用しています。

1. **IndexedDB を確認** → キャッシュがあればそれを返す（ネットワーク通信なし）
2. **ネットワークから取得** → キャッシュがなければサーバーから取得
3. **自動キャッシュ** → 取得成功 & 5MB以下なら IndexedDB に保存

```
ユーザーがファイルを開く
    ↓
Service Worker が介入
    ↓
IndexedDB にキャッシュあり？
    ├─ YES → 即座に表示（オフライン可）
    └─ NO  → サーバーから取得 → 5MB以下なら保存
```

#### 3.2.2 最適化画像（`/_next/image`）

Next.js の画像最適化を通したリクエスト（Markdown 内の画像、サムネイルなど）も自動キャッシュされます。

1. **Cache API を確認** → `optimized-images-v1` キャッシュを検索
2. **ネットワークから取得** → なければサーバーから取得し、Cache API に保存

> [!NOTE]
> **Cache API と IndexedDB の使い分け**
> - **通常ファイル**: IndexedDB（メタデータと一緒に管理するため）
> - **最適化画像**: Cache API（Next.js の標準的なキャッシュ方式）

### 3.3 Range リクエスト（部分取得）への対応

動画や音声ファイルなど、ブラウザが「部分的に取得」するタイプのファイルにも対応しています。

- Service Worker が `Range` ヘッダーを解析
- キャッシュされたファイルから指定範囲のみを切り出して返却
- HTTP 206（Partial Content）レスポンスを正しく生成

これにより、大きな動画ファイルでもシークバーを操作してスムーズに再生できます。

## 4. ストレージ容量の管理

### 4.1 サーバー側の容量制限

すべてのユーザーが共有するサーバーストレージには、以下の制限があります。

- **上限**: **3GB**（`SERVER_MAX_STORAGE_BYTES`）
- **判定タイミング**: ファイルアップロード時
- **超過時の動作**: HTTP 400 エラーを返し、アップロードを拒否

> [!CAUTION]
> **容量オーバー時の対処法**
> サーバー容量が不足している場合は、不要なメモや添付ファイルを削除してください。
> 削除後、同期が完了すればサーバー側の容量も解放されます。

### 4.2 クライアント側の容量管理（ガベージコレクション）

デバイスのストレージを圧迫しないよう、自動的に古いキャッシュを削除する仕組みがあります。

#### 削除のタイミング

新しいファイルを追加する際、以下の条件を満たすと自動的にガベージコレクション（GC）が実行されます。

```
現在のキャッシュ合計サイズ + 新規ファイルサイズ > CLIENT_MAX_STORAGE_BYTES
```

#### 削除の優先順位（LRU: Least Recently Used）

以下のルールで、古いキャッシュから順に削除されます。

| 優先度 | 対象 | 削除される？ |
|:---:|:---|:---|
| **最優先で保護** | 未同期データ（`isDirty: true`） | ❌ **絶対に削除されない** |
| **保護** | メタデータのみ（Blob なし） | ❌ 削除対象外 |
| **削除候補** | 同期済み（`isDirty: false`）かつ Blob あり | ✅ `lastAccessedAt` が古い順に削除 |

> [!IMPORTANT]
> **削除されるのは「ファイル実体（Blob）」のみ**
> ガベージコレクションで削除されるのはファイルの中身だけで、メタデータ（ファイル名、サイズなど）は残ります。
> そのため、一覧画面では引き続きファイル名が表示され、再度開く際にサーバーから取得されます。

#### 削除の流れ

1. 新規ファイル追加時に容量チェック（`checkAndGC`）
2. 容量不足を検出
3. 同期済みファイルを `lastAccessedAt`（最終アクセス日時）が古い順にソート
4. 必要な空き容量が確保できるまで、Blob を削除（`blob = undefined`）
5. メタデータは保持

## 5. 実際の動作シナリオ

### シナリオ1: オフラインでメモを作成

1. **ユーザー操作**: 地下鉄の中で新しいメモを作成し、画像を添付
2. **アプリの動作**:
   - メモと画像を IndexedDB に保存（`isDirty: true`）
   - 一覧画面に即座に表示
   - 画像のプレビューも表示可能
3. **オンライン復帰後**:
   - 自動的に同期処理が開始
   - メモと画像がサーバーにアップロード
   - `isDirty: false` に更新

### シナリオ2: 複数デバイスでの同時編集

1. **PC で編集**: 「会議メモ」の内容を更新（9:00）
2. **スマホで編集**: 同じ「会議メモ」を別の内容に更新（9:01）
3. **同期時の動作**:
   - サーバーが競合を検出
   - スマホに選択肢を表示
   - ユーザーが「ローカル優先」を選択
   - スマホの内容でサーバーを上書き
   - PC で次回同期時、スマホの内容が反映される

### シナリオ3: 大きなファイルの閲覧

1. **オンライン時**: 10MB の動画ファイルを開く
   - Service Worker がサーバーから取得
   - 5MB を超えるため、自動キャッシュ**されない**
2. **オフライン時**: 同じ動画を開こうとする
   - キャッシュがないため、表示できない
   - 「オフラインのため表示できません」とエラー表示

### シナリオ4: ストレージ不足時の自動削除

1. **状況**: デバイスのキャッシュ容量が上限に近い
2. **ユーザー操作**: 新しく 3MB のファイルを添付
3. **アプリの動作**:
   - 容量不足を検出（`checkAndGC` 実行）
   - 最も古い同期済みファイルの Blob を削除
   - 3MB 以上の空き容量を確保
   - 新しいファイルを保存
4. **削除されたファイルを再度開く場合**:
   - メタデータは残っているため、ファイル名は表示される
   - 開こうとすると、サーバーから再取得
   - 再取得後、再びキャッシュされる

## 6. トラブルシューティング

### Q1. オフラインで作成したメモが同期されない

**考えられる原因**:
- ネットワーク接続が不安定
- サーバー容量が上限に達している
- 認証エラーが発生している

**対処法**:
1. ネットワーク接続を確認
2. 画面を手動でリロード（同期が再試行される）
3. ブラウザのコンソールでエラーを確認

### Q2. 添付ファイルが表示されない

**考えられる原因**:
- ファイルがキャッシュされていない
- オフライン状態で未キャッシュファイルを開こうとしている

**対処法**:
1. オンライン状態で一度ファイルを開く（自動キャッシュされる）
2. 5MB を超えるファイルは自動キャッシュされないため、オンライン時のみ表示可能

### Q3. 同期エラーが頻発する

**考えられる原因**:
- 複数のタブで同時に RinSecretary を開いている
- IndexedDB のバージョン競合

**対処法**:
1. 他のタブを閉じる
2. ページをリロード
3. ブラウザのキャッシュをクリア（最終手段）

## 7. 技術的な詳細（開発者向け）

### 7.1 使用技術スタック

| レイヤー | 技術 | 役割 |
|:---|:---|:---|
| クライアント DB | Dexie.js (IndexedDB) | ローカルデータストア |
| サーバー DB | PostgreSQL (Prisma) | クラウドバックアップ |
| キャッシュ制御 | Service Worker | リクエスト介入・オフライン対応 |
| 同期管理 | SyncManager クラス | 同期ロジックの中枢 |

### 7.2 主要なファイル

- `src/worker/index.ts`: Service Worker の実装
- `src/lib/sync-manager.ts`: 同期ロジック
- `src/lib/db.ts`: IndexedDB スキーマ定義
- `src/lib/storage.ts`: サーバー容量管理
- `src/lib/constants.ts`: 容量制限などの定数定義

### 7.3 IndexedDB スキーマ

#### `memos` テーブル

| フィールド | 型 | 説明 |
|:---|:---|:---|
| `id` | string | メモID（UUID） |

| `content` | string | 本文 |
| `isDirty` | boolean | 未同期フラグ |
| `isDeleted` | boolean | 削除済みフラグ |
| `lastAccessedAt` | Date | 最終アクセス日時（LRU用） |
| `isFullContent` | boolean | 全文取得済みフラグ |

#### `attachments` テーブル

| フィールド | 型 | 説明 |

| `fileName` | string | ファイル名 |
| `mimeType` | string | MIME タイプ |
| `fileSize` | number | ファイルサイズ（バイト） |
| `filePath` | string? | サーバーパス |
| `blob` | Blob? | ファイル実体（キャッシュ） |
| `isDirty` | boolean | 未同期フラグ |
| `isDeleted` | boolean | 削除済みフラグ |
| `lastAccessedAt` | Date | 最終アクセス日時（LRU用） |

## 8. まとめ

RinSecretary のオフライン機能は、以下の3つの柱で成り立っています。

1. **ローカルファースト設計**: すべてのデータをまずデバイスに保存
2. **自動同期**: オンライン復帰時に自動的にクラウドと同期
3. **賢いキャッシュ**: よく使うファイルを自動保存し、古いものは自動削除

この仕組みにより、**いつでも、どこでも、快適に**メモを取ることができます。
