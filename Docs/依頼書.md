# Rimini 開発依頼書

## 1. 概要

- このプロジェクトは、RinSec を0ベースで再構築するものである。タスク、スケジュール、アラーム、メモを管理するためのアプリケーションであり、基本的にオフラインで高速に動作する。
- 前のプロジェクト（RinSec）のスクリプトやPrismaの定義などは `Docs/前のプロジェクト.txt` に記載されているため、適宜参考にする。特にUIや見た目、画面構成、何をページにして何をFABにするかなどは、前のプロジェクトをベースにして設計すること。

## 2. 技術スタック

- **Framework**: Next.js
- **Language**: TypeScript
- **Styling**: Material UI
- **State/Client DB**: Dexie.js (IndexedDB)
- **ORM**: Prisma
- **Database**: SQLite (開発・本番ともにパスベースのファイルDB `%DATABASE_URL%` を利用。サーバー側マスターデータ用)
- **Authentication**: 独自アカウント認証をベースとする
- **Data Sync Architecture**: Local-First (オフラインファースト) アーキテクチャ。基本データはクライアント側DB（Dexie.js等）に保存・処理され、バックグラウンドまたは明示的なタイミングでサーバーDBと同期される仕組みを構築する。

## 3. 機能要件

以下の情報を管理・永続化する機能群を構築してください。
タイトルや名前などの文字数は基本的に最大50文字とする。長い文字列かつ改行できないUIに表示する場合は、基本的に「...」で省略して表示する。
ここにあるタスクなどの要件で基本項目を指定するが、データベースの構造を強制的に指定するものではない。作成日時やその他技術的に必要になる項目は適宜追加すること。
タスク、イベント、アラーム、メモ、添付ファイル は 基本的にローカルで完全に動作するが、適切なタイミングでオンラインサーバーと同期される。

同期状態は明示的に示すようにする。
同期ステータスとして、青（完全同期から5分以内）、緑（同期から5分以内）、黄色（同期から5分以上）、赤（同期中にエラーなどが発生し失敗）の段階を設ける。
※ 完全同期とは、Googleカレンダーなども含めすべての同期が行われたことを指す。

同期先は以下の通りとする。

- イベント <-> SQLite <-> Googleカレンダー
- タスク <-> SQLite
- アラーム <-> SQLite
- メモ <-> SQLite
- ファイル <-> SQLite および サーバーディレクトリ

同期する際にコンフリクト（同期リクエスト元の最終同期時刻が、リクエスト先の更新時刻より前など）が起きたら、その解決をユーザーに委ねる（前のプロジェクト参考）。

タスク、イベント、アラームは、カード表示および編集モーダルのUI形態があり、カード表示はタイトルや時間などなるべくシンプルな情報に限る（前のプロジェクト参考）。
※ アラームは枠無しカード表示をしてスペースを取らないようにする。

### アカウント・設定

1. **ユーザーアカウント・各種設定管理**:
   - ユーザーは、パスワード、名前（重複不可、識別ID）、ニックネーム(重複可能)、プラン情報（Proプラン, 無料プラン）を持ち、セキュリティに厳重に配慮する。他人から個人のタスクやファイルなどのデータに絶対にアクセスさせてはならない。
   - タイムゾーン設定、一日の開始時刻(デフォルトは4:00)
   - Googleアカウント、AIツール、Discord webhook、Pushover などとの紐づけの設定(AI機能は後に追加するからまだ実装しないこと。Google垢やAIは複数と連携可能)。
   - 各種ツールの詳細設定。

### UI構成

- **メイン画面**:
  - 基本的に前のプロジェクトのメインと同じような設計で構築する。その日（例: 4時 - 翌日4時）のイベント、アラームが混在して時刻順に整列しており、その下にタスクが締切時刻順に整列する。縦スクロールで一覧をスクロールでき、横スワイプで次のページにスナップ移動可能なUIとする。
- **メイン画面のヘッダー**:
  - 左に日付、右にハンバーガーメニューを配置し、設定項目やツールのアイテムを格納する（前のプロジェクトを参考）。
- **メモ一覧画面**:
  - 前のプロジェクトを参考に設計する。サムネイル表示を含めること。
- **メモ閲覧画面 / メモ編集画面**:
  - （機能要件を満たすよう適宜実装する）
- **右下のFAB (Floating Action Button)**:
  - メイン操作は基本的にFABをトリガーとする。

### 管理対象エンティティ

2. **イベント**:
   - 基本項目: タイトル、開始日時、終了日時、メモ（通常のメモと同様に、Markdownやファイルに対応し、表示の実装を共通化する。メモ編集画面でも編集可能にすること）。
   - 複数のGoogleカレンダーと連携できること。

3. **タスク**:
   - 基本項目: タイトル、開始日時、期限の日時、タスクにかかる想定時間（秒単位）、データ（JSON形式の文字列。後の機能拡張（進捗やチェックリスト等）に柔軟に対応できるように設置）、メモ。

4. **アラーム**:
   - 基本項目: タイトル、通知日時、メモ。
   - その時刻になったら、Pushoverで通知を送信する。

5. **メモ**:
   - 基本項目: タイトル（内容から自動的に設定される。アルゴリズムは前のプロジェクト参考）、内容（最大1万文字）。
   - 前のプロジェクト同様に、Markdownや数式などの表示に対応し、ファイル添付を可能とする（ファイルの表示方法は前のプロジェクト参考）。

6. **添付ファイル**:
   - ファイルはメモに帰属する形で管理される。メモが消滅したらファイルも消滅する。他のユーザーや外部から基本的に閲覧不可とする。`data/uploads` フォルダで管理する。扱えるファイル形式は完全自由とする。アップロードファイルの上限は一切設けず無制限（無限GB）とする。ただし、Proプランならサーバー内の合計アップロードサイズ（ディレクトリのサイズ）を一定上限値（例: 3GB）以内に収め、無料プランなら、サーバー上限値かつユーザーごとに一定上限値（例: 10MB）に収める。
   - ファイルはアップロードと削除のみサポートし、編集は不可とする。

7. **ジョブ**:
   - 巨大ファイルアップロードやAI処理などの時間のかかる処理は、画面を離れても継続されるようにジョブで管理する。
   - ジョブはジョブ管理画面から確認や中断ができるようにする。

8. **システム全体のグローバル設定**:
   - アプリケーション全体で使う共通の設定値（例: 全体の容量制限やタスク・イベントごとのイメージカラーなど）は共通化して管理する。

## 4. テスト要件

テストは以下のフローを完全に満たしていること。

- **E2Eテストのみ実施 (Playwright)**:
  - Playwrightを用いたE2Eテストで品質を担保すること。
  - リポジトリ構成内に `playwright.config.ts` を用意すること。
  - テスト失敗時のトレースやビデオ記録を行い、ブラウザはデスクトップ版 Chromium (`Desktop Chrome`) を利用する。
  - **重要**: モバイル表示 (`isMobile: true`) をシミュレートしたテストを中心にし、エディタ等が安定稼働するように調整すること。
  - `webServer` 項で、本番ビルドされたコード (`npm run build`) をポート3001で起動させつつ、別途テスト用データベース (`test.db`) を用いて E2E テストを実行する仕様とする。

## 6. 非機能要件・UI/UXとアーキテクチャルール

開発・実装にあたり、以下のプロジェクト特有のルールを遵守すること。

- **モバイルファースト・ホバー不使用**:
  - モバイル端末（スマートフォン）での利用を最優先にUIを構築すること。
  - ホバー（Hover）による情報表示やアニメーション・スタイル変更などは一切実装しない。
  - デバイス判定機構（画面幅だけでなく、JavaScript等でポインティングデバイスの精度やホバー可否を判定する仕組み）を実装し、ポインタとホバーが利用可能な環境かを判定すること。
- **非同期処理のジョブ化ルールの徹底**:
  - LLM（AI生成）、ファイルアップロード、各種重い処理（5秒以上）は、直接APIのレスポンスでブロックせず、専用の非同期ジョブ管理機構に処理を登録（IDを発行）し、バックグラウンド処理として稼働させること。
  - クライアントからは、発行されたIDを用いて進行状況や完了ステータスをポーリング等で取得できるようにすること。
- **バッチ・スケジューラーの構築**:
  - Node.js で動作する定期タスク用スケジューラースクリプト（毎日指定時刻や定間隔でDBをチェックし、タスクを自動生成・更新するような常駐プログラム）を構築し、本体起動プロセス（`next dev` コンテナや `node server.js` に併走する形等）で常駐・動作させること。
- **ストレージ容量制限**:
  - システム全体のグローバルな設定情報として、最大ディスク使用量（Global Storage Limit: 例 3GB制限）を管理すること。
  - ファイルの保存・削除時にシステム全体の容量状況を一元管理して足し引きする処理を厳格に行い、上限を超える場合は一律でアップロードを拒否すること。単一ファイルサイズ自体の制限は設けない。
- **コーディング思想・品質**:
  - **型安全の徹底**: 日本語ベースのコードベースにおいても、TypeScriptの型システムを最大限活用し、`any` や `as` の使用を原則禁止すること。
  - **根本解決の追求**: 対処療法的な修正ではなく、問題の根本原因を解決する設計・実装を心がけること。
  - **保守性の維持**: モジュール分割、コードの共通化、責務の分離を徹底し、変更に強く追いやすいコードを維持すること。
  - **不要な記述の削除**: 変更により使われなくなったコードや定数は放置せず、即座に削除すること。
  - **ローカルタイムの意識**: 日本語ユーザーを想定し、常に `Asia/Tokyo` (JST) を意識した実装（UTCとの変換ミス防止）を徹底すること。
  - フロントエンド通信量、フロントエンド電力量、APIリクエスト回数、空間計算量、時間計算量を最小化するような設計・実装を行うこと。常に「データが1億件あったら」という前提を念頭に置くこと（データ量が少ないことが自明な場合はその限りではない）。

## 7. アーキテクチャ要件 (ローカルファースト・同期型)

- **基本データフロー**: 全てのCRUD操作（タスク、メモなど）は、まず**クライアント側（ブラウザ内の IndexedDB / Dexie.js）に対して行われ、UIに即座に反映**されること。
- **サーバー同期**:
  - オンライン状態の際、バックグラウンドでのポーリング、または変更発生時をトリガーとして、変更分をサーバー（Prisma/SQLite）へ同期・永続化する仕組みを構築する。
  - レスポンス待ちによるUIのブロッキングを防ぐため、通信はあくまで非同期とし、メインスレッドをブロックしないこと。
- **認証と連携**:
  - 最初からGoogleアカウント等の構成を必須とせず、独自のID/パスワード（または単一ログイン用の仕組み）など独立したアカウントで開始できること。

## 8. スモールステップ・テスト駆動開発 (TDD)

開発は一度に全機能を実装するのではなく、**必ずテスト駆動開発（TDD）に基づいたスモールステップ**で進行すること。
以下のサイクルを厳格に守って開発を進め、着実かつ検証可能なステップで開発を進めること。

1. **ステップの細分化**:
   - 機能ごとに極力小さなタスク（例: 「Taskテーブルのスキーマ定義とCRUD処理APIの実装」など）に分割する。
2. **テストの先行記述 (Red)**:
   - 実装を始める前に、必ず要件を満たす Playwright を用いた E2Eテスト を記述する。
   - テストを実行し、意図通りに「失敗」することを確認する。
3. **最小限の実装 (Green)**:
   - テストをパスさせるための「最小限のコード」のみを実装する。
4. **リファクタリング (Refactor)**:
   - テストが通った状態を維持しつつ、Lint(ESLint)の修正、TypeScriptの型見直し、コードの共通化・整理を行う。
5. **レビューとコミット**:
   - 1つの小さな機能（およびそのテスト）が完成するごとに、動作確認を行う。

## 9. コーディング手順

基本的に以下の順番で開発を回すこと。

1. すべき事を明確にする。
2. E2E テストコードでテストすべき事を考える。
3. 既存コードがないか、共通化して流用できそうなコードはないか確認する。
4. コーディングする（この際、型を厳格に意識すること）。
5. Lintの静的チェックを行いエラーを解消する（この際、その場しのぎの修正ではなく根本解決を行うこと）。
6. 再びLintの静的チェックを行いエラーが0になるまで修正を続ける。
7. コンパイルチェックを行いエラーを解消する（この際、その場しのぎの修正ではなく根本解決を行うこと）。
8. 再びコンパイルチェックを行いエラーが0になるまで修正を続ける。
9. E2Eテストを行いエラーが0になるまで修正を続ける（この際、その場しのぎの修正ではなく根本解決を行うこと）。
10. Lint、コンパイル、E2Eテストすべてが完全に通ったら、やった事を日本語でユーザーに伝える。

Lint、コンパイル、E2E において、コード修正をおこなう場合は、以下のようなループを行う

- Lintチェック -> コード修正 -> Lintチェック -> コード修正 ... -> Lintチェック(エラー0)
- コンパイルチェック -> コード修正 -> Lintループ(エラー0) -> コンパイルチェック -> コード修正 ... -> Lintループ(エラー0) -> コンパイルチェック(エラー0)
- E2Eテスト -> コード修正 -> Lintループ(エラー0) -> コンパイルループ(エラー0) -> E2Eテスト -> コード修正 ... -> Lintループ(エラー0) -> コンパイルループ(エラー0) -> E2Eテスト(エラー0)
