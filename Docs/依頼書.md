# Rimini 開発依頼書 (フルスクラッチ再構築)

## 1. 概要

- 既存のソースコードは提供しません。本資料に記載された技術スタック、データベーススキーマ、テスト手法、デプロイ手法を完全に再現および構築してください。

## 2. 技術スタック

### フロントエンド・バックエンド

- **Framework**: Next.js (App Router / `src/app`ディレクトリベース)
- **Language**: TypeScript
- **Styling**: Vanilla CSS, Emotion, Material UI (MUI v5/v7)
- **Component Libraries**: `framer-motion`, `swiper`, `react-draggable`, `react-window`
- **Editor**: Monaco Editor (`@monaco-editor/react`)
- **Markdown Rendering**: `react-markdown`, `remark-gfm`, `remark-math`, `rehype-katex`, `katex`
- **Charts**: ApexCharts (`react-apexcharts`)
- **State/Client DB**: Dexie.js (IndexedDB)
- **Date Validation & Formatting**: `date-fns`

### バックエンド機能

- **ORM**: Prisma
- **Database**: SQLite (開発・本番ともにパスベースのファイルDB `%DATABASE_URL%` を利用。サーバー側マスターデータ用)
- **Authentication**: 独自アカウント認証 (Credentials, Email/Password等) をベースとする。Google OAuth等は**後からアカウントに紐付け可能（連携）**なオプションとする。
- **Data Sync Architecture**: Local-First (オフラインファースト) アーキテクチャ。基本データはクライアント側DB（Dexie.js等）に保存・処理され、バックグラウンドまたは明示的なタイミングでサーバーDBと同期される仕組みを構築する。
- **External Integrations**: OpenAI / Gemini / Anthropic SDKs (AI API連携), Google APIs

### インフラ・その他

- **Platform**: Node.js (v20)
- **Container**: Docker (docker compose用 / `Dockerfile` にてマルチステージビルド)
- **Utility**: `tsx`, `concurrently` (ローカル開発サーバー併走用)

## 3. データベース・機能要件

以下の情報を管理・永続化する機能群を構築してください。（具体的なテーブル名やカラム名、データ構造は開発業者が最適な設計を行って構いませんが、以下のすべての機能要件を満たす必要があります）

1. **ユーザーアカウント・各種設定管理**:
   - アカウントごとの基本情報、メールアドレス、パスワード等。
   - ユーザーごとのAI機能利用設定（利用するAIプロバイダ、APIキー、利用するモデル名、接続先URL、思考プロセスの表示設定など）。
   - 外部サービス連携設定（メール要約に使う指示文やモデルの選択、通知サービスのユーザーキー、通知を送信するWebhookのURLなど）。
2. **セッションおよび外部プロバイダログイン連携**:
   - OAuth連携におけるプロバイダ名、プロバイダ側のカウントID、アクセストークン等の保持。
   - 後からGoogle等外部プロバイダ連携を紐付けできる拡張性を持った管理機構（OAuthのアカウントリンク要件を満たすこと）。
3. **タスク管理**:
   - 個別タスクのタイトル、詳細なメモ、開始日、期限の設定。
   - 現在の進捗度合い（パーセンテージや進捗バーなどの数値）の管理。
   - タスクに関連するチェックリスト（サブタスク）の保持。
4. **定期タスク管理**:
   - 日次(Daily)や週次(Weekly)など、定期的に繰り返し発生するタスクの設定。
   - 定期生成時に適用されるチェックリストのひな形（テンプレート）の管理。
   - 管理上の有効・無効（一時停止）フラグの保持。
5. **アラーム・通知管理**:
   - 特定の予定やタスクに対する事前通知など、指定した日時に通知を発火させるための設定情報。
   - 通知の処理状況（送信済み、未送信などの状態管理）。
   - 通知に関連付けるコメントやメモの保持。
6. **ノート（メモ）機能**:
   - 作成したドキュメントのタイトルと本文データの保存。
   - ノート一覧で表示するためのサムネイル画像情報の保持。
7. **添付ファイル管理**:
   - ノート等に添付されるファイルの名称、保存場所、ファイルサイズ、ファイルの種類などの情報の管理と、対象ドキュメントへの紐付け機能。
8. **メール要約およびフィルタリング**:
   - ユーザーが受信したメールの内容、AIによる要約結果、関連するリンク、送信元、および処理の状態（成功、失敗、未読など）を管理する機能。
   - 要約したくない特定の送信者を指定できるブロックリスト機能。
9. **外部ストレージバックアップ設定**:
   - 表示上のフォルダ名、Google Drive 等のフォルダID、バックアップの有効・無効設定を保持。
   - 最終バックアップ結果（成功・失敗の状態、実行日時、エラーメッセージ）の記録。
10. **一時ファイル共有**:
    - 公開用ファイル名、保存先、ファイルサイズ、ファイルの種類、発行日時などの管理。
11. **非同期ジョブ（バックグラウンド処理）の追跡**:

- AIによる生成処理やバックアップ、メール処理などが今どのような状況か（実行中、完了、エラーなど）を確認できる仕組み。

12. **システム全体のグローバル設定**:

- アプリケーション全体で使う共通の設定値（例: 全体の容量制限や現在の使用量など）を保存できる仕組み。

## 4. テスト要件

テストは以下のフローを完全に満たしている必要があります。

- **タイムゾーン制約**: タイムゾーン `TZ=Asia/Tokyo` を環境変数として必須とします。
- **E2Eテストのみ実施 (Playwright)**:
  - 単体テスト（Unit test）は不要です。Playwrightを用いたE2Eテストのみで品質を担保してください。
  - リポジトリ構成内に `playwright.config.ts` を用意すること。
  - テスト失敗時のトレースやビデオ記録を行い、ブラウザはデスクトップ版 Chromium (`Desktop Chrome`) を利用します。
  - **重要**: モバイル表示(isMobile: true)をシミュレートしたテストを中心にし、エディタ等が安定稼働するように調整してください。
  - `webServer` 項で、本番ビルドされたコード (`npm run build`) をポート3001で起動させつつ、別途テスト用データベース (`test.db`) を用いて E2E テスト (`npm run test:e2e:sync` / UIモード `test:e2e:sync:ui`) を実行する仕様にします。

## 5. デプロイ要件 (CI/CD GitHub Actions)

**※重要: 既存のデプロイ関連ファイル等は一切提供しません。インフラ構築およびデプロイフローの整備においては、以下のステップを要件として、GitHub Actionsのワークフローファイル（`.github/workflows/deploy.yml` 等）や必要な環境構築スクリプトを新規作成・構築してください。**

以下のステップが自動化されたCI/CDパイプラインを組むこと。

1. **ジョブ `test`**:
   - `ubuntu-latest`, Node.js (v20) 上でリポジトリをチェックアウトし、`npm ci` を実行。
   - `npm run test:time` で E2E/Timezone テストをすべてクリアする。
2. **ジョブ `build-and-push`**:
   - `test` 完了後、Docker Buildx をセットアップ。
   - `ghcr.io` に GitHub Token を使ってログインし、Dockerイメージ (`ghcr.io/リポジトリ名:latest`) をビルド、プッシュする。キャッシュ(gha)を有効活用する。
3. **ジョブ `deploy`**:
   - VPS サーバーに SSH接続 (Host, User, Port, KeyをSecretsから利用)。
   - リポジトリ(mainブランチ)をVPS上にクローン/Pullして最新化。
   - プロジェクト用の環境設定ファイルを、認証用URLや認証用シークレットなどの機密情報から動的に生成。
   - データディレクトリ・永続化ディレクトリ (`data/`, `data/uploads/`) を作成し、Dockerコンテナ実行ユーザー (uid 1001想定) に合わせて適切にパーミッション(権限)を付与する。
   - データベースファイルがある場合、管理用の通知機能を用いてデータベースファイルを送信・バックアップする。
   - `docker compose pull` , `docker compose up -d` コマンドでサービスをコンテナ起動・更新する。
   - デプロイの完了を同じ Discord Webhook にテキスト通知する。

## 6. 非機能要件・UI/UXとアーキテクチャルール

開発・実装にあたり、以下のプロジェクト特有のルールを遵守すること。

- **モバイルファースト・ホバー不使用**:
  - モバイル端末(スマートフォン)での利用を最優先にUIを構築すること。
  - ホバー(Hover)による情報表示やアニメーション・スタイル変更などは一切実装しない。
  - デバイス判定機構 (画面幅だけでなく、JavaScript等でポインティングデバイスの精度やホバー可否を判定する仕組み) を実装し、ポインタとホバーが利用可能な環境かを判定すること。
- **非同期処理のジョブ化ルールの徹底**:
  - LLM（AI生成）、ファイルアップロード、各種重い処理（5秒以上）は、直接APIのレスポンスでブロックせず、専用の非同期ジョブ管理機構に処理を登録（IDを発行）し、バックグラウンド処理として稼働させること。
  - クライアントからは、発行されたIDを用いて進行状況や完了ステータスをポーリング等で取得できるようにすること。
- **バッチ・スケジューラーの構築**:
  - Node.js で動作する定期タスク用スケジューラースクリプト（毎日指定時刻や定間隔でDBをチェックし、タスクを自動生成・更新するような常駐プログラム）を構築し、本体起動プロセス(`next dev` コンテナや `node server.js` に併走する形等)で常駐・動作させること。
- **ストレージ容量制限**:
  - システム全体のグローバルな設定情報として、最大ディスク使用量 (Global Storage Limit: 例 3GB制限) を管理すること。
  - ファイルの保存・削除時にシステム全体の容量状況を一元管理して足し引きする処理を厳格に行い、上限を超える場合は一律でアップロードを拒否すること。単一ファイルサイズ自体の制限は設けない。
- **その他 (コーディング思想・品質)**:
  - **型安全の徹底**: 日本語ベースのコードベースにおいても、TypeScriptの型システムを最大限活用し、`any` や `as` (Type Assertion) の使用を原則禁止（または極限まで制限）してください。
  - **根本解決の追求**: 対処療法的な修正ではなく、問題の根本原因を解決する設計・実装を心がけてください。
  - **保守性の維持**: モジュール分割、コードの共通化、責務の分離を徹底し、変更に強く追いやすいコードを維持してください。
  - **不要な記述の削除**: 変更により使われなくなったコードや定数は放置せず、即座に削除してください。
  - **ローカルタイムの意識**: 日本語ユーザーを想定し、常に `Asia/Tokyo` (JST) を意識した実装（UTCとの変換ミス防止）を徹底してください。

## 7. アーキテクチャ要件 (ローカルファースト・同期型)

- **基本データフロー**: 全てのCRUD操作（タスク、メモなど）は、まず**クライアント側（ブラウザ内の IndexedDB / Dexie.js）に対して行われ、UIに即座に反映**されること。
- **サーバー同期**:
  - オンライン状態の際、バックグラウンドでのポーリング、または変更発生時をトリガーとして、変更分をサーバー(Prisma/SQLite)へ同期・永続化する仕組みを構築する。
  - レスポンス待ちによるUIのブロッキングを防ぐため、あくまで通信は非同期とし、メインスレッドをブロックしない。
- **認証と連携**:
  - 最初からGoogleアカウント等の構成を必須とせず、独自のID/パスワード（または単一ログイン用の仕組み）など独立したアカウントで開始できること。
  - そのアカウントに対して、後からGoogleアカウント等を「連携先プロバイダ」として追加・紐付けられる設計（OAuthのアカウントリンク機能）とすること。

## 8. 開発手順 (スモールステップ・テスト駆動開発: TDD)

開発は一度に全機能を実装するのではなく、**必ずテスト駆動開発（TDD）に基づいたスモールステップ**で進行してください。
以下のサイクルを厳格に守って開発を進めること。

1. **ステップの細分化**:
   - 機能ごとに極力小さなタスク（例: 「Taskテーブルのスキーマ定義とCRUD処理APIの実装」など）に分割する。
2. **テストの先行記述 (Red)**:
   - 実装を始める前に、必ず要件を満たす Playwrightを用いた E2Eテスト を記述する。
   - テストを実行し、意図通りに「失敗」することを確認する。
3. **最小限の実装 (Green)**:
   - テストをパスさせるための「最小限のコード」のみを実装する。
4. **リファクタリング (Refactor)**:
   - テストが通った状態を維持しつつ、Lint(ESLint)の修正、TypeScriptの型見直し、コードの共通化・整理を行う。
5. **レビューとコミット**:
   - 1つの小さな機能（およびそのテスト）が完成するごとに、動作確認を行った上でコミット（可能であれば依頼元への中間報告・確認）を実施する。

いきなりの大規模なプルリクエストや、テストの伴わない実装の提出は受け付けません。着実かつ検証可能なステップで開発を進めてください。

## 9. 開発ロードマップ・スモールステップの実装例

全機能を一度に実装するのを防ぐため、以下の順序を参考にして TDD サイクルを回しながら開発を進めてください。

### フェーズ 1: プロジェクトのリポジトリ構築とCIセットアップ (Scaffolding & CI)

- **Step 1.1**: Next.js、TypeScript、Playwright 等を用いた開発・テスト基盤の初期構築。
- **Step 1.2**: 継続的インテグレーション（CI）環境での自動テスト実行 GitHub Actions ワークフローの作成。

### フェーズ 2: サーバー側データベースとAPI基盤の構築 (Server DB & API Foundation)

- **Step 2.1**: PrismaとSQLiteを用いたバックエンド側のデータベーススキーマの定義と初期化。
- **Step 2.2**: クライアントから呼び出されるAPIの基本的なルーティング構造とエラーハンドリングの構築。

### フェーズ 3: 独自認証システムの構築 (Local Auth)

- **Step 3.1**: メールアドレスやパスワード等を用いた独自アカウントベースのサインアップ基盤の実装。
- **Step 3.2**: 独自認証に基づいたセッション管理機能とログイン画面の構築。
- **Step 3.3**: 認証が必要なページへのアクセス制限やリダイレクト処理（保護されたルート）のテスト。

### フェーズ 4: ローカルファースト基盤の構築 (Local-First Base Setup)

- **Step 4.1**: Dexie.js等を用いたクライアント（ブラウザ）上のローカルデータベース環境（IndexedDB基盤）の構築。
- **Step 4.2**: サーバーとの通信が行えなくても、ローカルDBのみでアプリケーションが立ち上がるオフライン動作の基本テスト。

### フェーズ 5: データ同期アーキテクチャの確立 (Data Sync Architecture)

- **Step 5.1**: クライアント上の変更を定期的にサーバーへ送信・反映するためのポーリングまたはバックグラウンドSync APIの構築。
- **Step 5.2**: サーバー側からの変更をローカルに反映させるための差分同期ロジックの構築とE2Eテスト。

### フェーズ 6: システム設定と容量管理 (System Config & Quota)

- **Step 6.1**: システム全体レベルのデータを保持するKey-Valueストア（システム設定機能）の実装。
- **Step 6.2**: グローバルなストレージ容量を管理・集計し、総容量の上限を制御するロジックの構築。

### フェーズ 7: 基本タスク管理の構築 (Core Task Management)

- **Step 7.1**: タスクの作成機能（タイトル、期限、メモ等の入力）をローカルデータベース優先で実装。
- **Step 7.2**: タスクの進行状態（進捗バー等）やチェックリストを管理・更新できるUIの構築。
- **Step 7.3**: オフラインで作成したタスクが、オンライン復帰時にサーバーへ正しく同期・保存されることのE2Eテスト。

### フェーズ 8: スケジュール表示と定期タスク生成 (Scheduling & Recurring Tasks)

- **Step 8.1**: 自動で繰り返し設定される「定期タスク」の生成テンプレートの作成と、該当条件に基づくスケジューリングロジックの構築。

### フェーズ 9: ノート（メモ）機能の構築 (Rich Text Notes)

- **Step 9.1**: リッチテキストとして記述可能なノート（メモ）の作成・編集機能の実装。
- **Step 9.2**: ノートの作成・詳細表示・編集機能、および変更のオフラインでの同期機能のE2Eテスト。

### フェーズ 10: デバイス最適化とUI調整 (Mobile-First UI/UX)

- **Step 10.1**: スマートフォン実機を想定したUI/UX調整（ホバー不使用の徹底など）。
- **Step 10.2**: 単なる画面幅判定ではなく、JavaScript等でポインティングデバイスの精度やホバー可否を判定する仕組みの統合。

### フェーズ 11: ファイル管理とアップロード (File Attachments & Sharing)

- **Step 11.1**: ノート作成時に画像等のファイルをアップロード・添付できる機能の実装。
- **Step 11.2**: アップロード時にファイルサイズを集計し、フェーズ6で作成したシステム上限で一律拒否する制御のE2Eテスト。
- **Step 11.3**: URLなどで他のユーザー等に一時的に発行・共有できる「一時共有ファイル」管理機能の構築。

### フェーズ 12: 非同期ジョブ処理基盤の確立 (Async Job System)

- **Step 12.1**: 裏で重い処理を実行するための「非同期ジョブ機構」のテーブル定義と管理ロジックの構築。
- **Step 12.2**: ジョブの実行状況（進行・完了・失敗）をクライアントからポーリング等で監視し、UIにプログレスバー等を表示する仕組み。

### フェーズ 13: オプション認証とバックアップ (OAuth & Database Backup)

- **Step 13.1**: 独自アカウントに対して、後からGoogleアカウント等（OAuth）を紐付けられる「アカウントリンク機能」の実装。
- **Step 13.2**: ユーザーのSQLiteデータベースファイルをGoogle Drive等へ自動または手動でエクスポートする「バックアップ機能」のジョブ処理への組み込み。

### フェーズ 14: 生成AI連携と自動処理機構 (AI Integrations)

- **Step 14.1**: ユーザーごとに複数のAIプロバイダ（OpenAI等）のAPIキーやモデルを設定できる管理画面の実装。
- **Step 14.2**: APIキーを用いて生成AIを呼び出しテキスト等の生成を行う機能。非同期ジョブ機構と連携してUIをブロックしない挙動のテスト。
- **Step 14.3**: メールの長文等を取り込みAIを使って自動的に要約する機能、および要約対象から特定の送信者をスパムとして除外するフィルタリングの実装。

### フェーズ 15: アラーム・常駐プロセスと最終検証 (Alarms, Cron & Final Polishing)

- **Step 15.1**: ユーザーが設定した特定の時刻にシステム内で「アラーム」等を発火・モバイル通知送信(Pushover等)する仕組みの構築。
- **Step 15.2**: Node.jsで常時稼働させる「定期タスク・アラーム等のチェッカースクリプト」の実運用連携テスト。
- **Step 15.3**: 本番稼働を模擬し、全フェーズの機能が連携したフローを通じた総合的なE2Eテストの完了とレビュー。
