# アプリ仕様詳細ガイド（Docs）作成ルール

## 基本方針
`Docs` フォルダ内に作成するドキュメントは、「アプリを利用する一般ユーザー」を読者として想定し、プログラムの知識がなくても機能や仕様を正しく理解し、活用できることを目的とする。

## 記述ガイドライン

### 1. ユーザー視点の徹底
- **「何ができるか」を主眼に置く**: コードの構造ではなく、ユーザーが操作した結果何が起きるか、どのようなメリットがあるかを記述する。
- **「ユーザーに見えるもの」を説明する**: 画面上の名称（ボタン名、ステータス名など）をそのまま使用する。

### 2. 技術情報の排除（重要）
- **ソースコード・ファイルパスの禁止**: `src/...` や `functions.ts` などのファイル名、変数名、関数名を本文中に含めない。
- **内部エンジンの名前を避ける**: 「Prisma」「Next.js」「スケジューラー」などの技術用語は、ユーザーが理解できる一般的な表現（「データベース」「アプリのシステム」「自動実行機能」など）に置き換える。

### 3. 動作条件の分かりやすい説明
- **内部ロジックの翻訳**: 「5分経過したか判定する」というロジックは、「5分以上操作がない場合」や「5分以上経過したとき」のように、ユーザーの行動や時間の経過として説明する。
- **具体例の活用**: 「すべてのデータが最新であること」など、抽象的な表現は具体例（カレンダー、タスク、アラームすべて）を列挙して補足する。

### 4. 構成と表現
- **Markdown形式**: 標準的な Markdown を使用する。
- **視覚的補助**: 複雑な流れを説明する場合は、Mermaid 図などを用いる。ただし、Mermaid 図内のテキストも非技術的な言葉を使用すること。
- **強調表示**: 重要な注意点や制限事項（削除のタイミング、復元不可など）は、引用や GitHub アラート（> [!IMPORTANT] 等）を使用して目立たせる。
- **最終更新日の記載**: タイトル（H1）のすぐ下に、`最終更新日: YYYY-MM-DD` の形式でそのドキュメントの最終更新日を記載すること。

## 運用
ドキュメント作成の依頼があった際、コンテキストとして `Docs` フォルダが指定されている場合は、本ルールを適用して内容を構成すること。
